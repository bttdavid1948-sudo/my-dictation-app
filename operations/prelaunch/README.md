## Learner data, deletion and retention — proposed policy for Owner decision

Actual inventory from canonical client/Rules: `user_vocab/{uid}` contains serialized private lessons; `users_profile/{uid}` contains nickname/profile/contact/preferences and learning totals; Auth contains Google identity; `community_units` is retained legacy author data, not a public catalog. Feedback may contain sender identity and learner-supplied free text. Local browser history/review/favorites use `xnot_{kind}_uid_{uid}`; guest versions remain separate. Session draft uses `man_private_draft_v1_{uid}`; study resume uses `man_study_v1` and generic Practice resume belongs to its recorded UID. Map exact generic runtime keys before deletion. Signing out is not deletion and local history is not cross-device cloud sync.

Owner decision proposal: active private lessons/profile remain until user deletes their content or requests account deletion; no automatic inactivity deletion in this scope. Feedback retention 90 days after triage, sanitized operational incident logs 30 days, minimum deletion case receipt 30 days after completion without message/lesson/phone/email content. These numbers are proposed, not current policy/implemented TTL. Legal holds/exceptions require documented Owner decision and minimum scope. Account request: acknowledge within 2 working days, target active-store completion within 7 days AFTER verified identity and exact scope approval. These are proposed service targets, not legal-compliance claims.

Request channel: existing Nhắn Chủ Xóm; additionally document an approved fallback support contact before launch. Do not invent an email address. Account deletion request must originate from a recently authenticated identity; do not ask for password/OTP or accept an email-only claim. Lost Google account → support/manual identity evidence review by Owner; no UID transfer/account-link/credential reset without separate approval. Content deletion through existing private editor affects lesson content, not Auth/account/feedback/legacy data.

Deletion procedure (not executed): (1) record case, exact UID/storage scope and authorized decision privately; (2) inventory ONLY that user's known records using existing least-privilege trusted read; inventory legacy author records without bulk scan if query suffices; (3) preserve minimal receipt/hash, not an extra archive of content scheduled for deletion; (4) suspend account/sessions only with explicit authority, guard writers; (5) delete verified active documents/legacy/feedback where requested and authorized, checking ownership at execution time; (6) delete Auth last and revoke sessions under explicit approval; (7) user clears ONLY their own browser-scoped local/session data and resume entries matching UID, including other devices. Do not clear all localStorage or other users/guest data. (8) read back active absence and inability to recreate through existing sessions; persist sanitized counts and backup-expiry obligation. Server deletion is irreversible through ordinary product flow: stop for required action-time confirmation. Never delete/migrate data while preparing this runbook.

Backup caveat: daily scheduled backups retain 7 days at the last verified configuration; existing managed exports/buckets may follow a DIFFERENT retention policy and must be inventoried before any promise of erasure. Do not promise all deleted data disappears within 7 days. Maintain a private minimal deletion exclusion register so restored backups do not resurrect requested-deleted records; apply exclusions inside an isolated restore before any return to service. New backup, export or deletion-register retention changes require explicit privacy/configuration approval. Check backup expiry and complete the case only when every scoped copy/exemption is accounted for. Public policy/support UI awaits Owner adoption; no legal guarantees are published.
